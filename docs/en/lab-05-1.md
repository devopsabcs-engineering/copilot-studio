Prepare infrastructure for the Search exercises without assuming that a successful Terraform deployment also creates an index, configures a new Foundry project, or grants the interactive user access. Allow 45–90 minutes for review and an approved deployment; quota requests can take longer.

> [!IMPORTANT]
> Source/static review only; live execution blocked. The supplied root Terraform files and child modules were inspected locally on 2026-10-19. Terraform is not installed in the review environment. No provider was downloaded, no plan or apply was executed, and no billable resource was created.

All commands below are instructions for a later operator session. They were not run during documentation preparation. Do not execute deployment or deletion commands without the resource owner's approval.

## Architecture and prerequisites

![Original bilingual diagram of the Terraform plan, review gate and intended Azure resources](../assets/lab-05-1/deployment.svg)

Figure 1. Original explanatory diagram, not a screenshot. The optional Foundry module is disabled in the supplied root configuration.

You need:

* An approved subscription, dedicated training resource group, budget owner, resource location and model location
* Azure CLI and a supported Terraform installation on your workstation
* Permission to create resources and to assign roles; Contributor alone cannot create role assignments
* Adequate Azure OpenAI deployment quota for the selected region, model, deployment type and capacity
* The complete authorized `scripts` directory, including its local `modules` subdirectories
* Secure storage for Terraform state and any credentials; an administrator-approved network design

The workshop suggests Azure CLI 2.50 or later and Terraform 1.5 or later. The actual root configuration accepts Terraform `>= 1.4.6`; this is a minimum constraint, not proof that every later release has been tested. Preserve a reviewed toolchain and provider lock file instead of selecting versions by date alone.

## 1. Inventory the supplied files before running anything

1. Work from an authorized local copy of the complete `scripts` directory. This documentation repository does not redistribute the protected source.
2. Confirm `main.tf`, `providers.tf`, `variables.tf`, and `outputs.tf` exist at the root.
3. Confirm local modules `vnet`, `mi`, `st`, `openai`, and `search` exist. An additional `ai-foundry` directory is present but its root module call is commented out.
4. Review provider constraints. The inspected root declares AzureRM `~> 4.45.1`, AzAPI `~> 1.0`, AzureAD `2.48.0`, and Random `3.6.1`.
5. Read each child module, not only the root variables. A variable name does not establish that its value is used.
6. Record a source version or an approved file-hash inventory in your private evidence store. Do not publish source paths, tenant details or state.

## 2. Establish the authorization and cost boundary

1. Ask the subscription owner to approve the target subscription, resource group, selected regions, maximum spend and cleanup date.
2. Distinguish the deployment identity, your interactive lab identity, the Search service identity and the Foundry project identity. They are not interchangeable.
3. Ensure the deployment identity can create role assignments at the chosen scope. Use Owner, User Access Administrator, Role Based Access Control Administrator, or an appropriate custom role together with resource-creation rights.
4. Have the administrator confirm required provider registrations, including `Microsoft.Search`, `Microsoft.CognitiveServices`, `Microsoft.Storage`, `Microsoft.Network`, and `Microsoft.ManagedIdentity`. Add `Microsoft.KeyVault` and `Microsoft.MachineLearningServices` only if the revised design actually needs them.
5. Estimate costs from resource SKUs, model capacities, storage, embeddings, semantic queries and later agent usage. `terraform plan` is not a pricing engine.
6. Select a network policy. If private access is required, stop until the configuration implements private endpoints, DNS and an approved Power Platform connectivity path.

The [Search RBAC reference](https://learn.microsoft.com/en-us/azure/search/search-security-rbac) separates object management from document read/write. The [Terraform authentication guide](https://learn.microsoft.com/en-us/azure/developer/terraform/authenticate/authenticate-to-azure) describes supported identity paths.

## 3. Configure a disposable operator workspace

1. Open PowerShell in your authorized working copy of `scripts`, not in the read-only source directory.
2. Verify tools without changing infrastructure:

   ```powershell
   az --version
   terraform version
   ```

3. Sign in only when required by your organization's process, then select the approved subscription. Keep real identifiers out of shared transcripts.
4. Create a private variable file using the supplied variable names. At minimum, set `subscription_id`, `resource_group_name`, `location`, and `location_azopenai`. The two location settings are independent.
5. Preserve unique resource names or the reviewed random suffix behavior. Global name availability is not guaranteed by a local plan.
6. Check that the working copy excludes `.env`, variable secrets, state, state backups, `.terraform`, and saved plans from publication. Retain the provider lock file under the team's approved versioning policy.
7. Review the network and identity findings above with the instructor. Stop here if required controls are absent. Documentation does not silently repair the supplied configuration.

Never print complete `terraform output -json`, state, debug logs, or environment files into an issue or screenshot. A value marked sensitive can still be present in state.

## 4. Initialize, validate and inspect the plan

These commands download modules/providers or query Azure when the operator runs them. They are not offline evidence from this review.

1. Initialize only the approved working copy:

   ```powershell
   terraform init
   ```

2. Validate formatting and configuration:

   ```powershell
   terraform fmt -check -recursive
   terraform validate
   ```

3. Resolve missing local modules, unsupported provider arguments and incompatible constraints before continuing. Do not upgrade all providers as an unreviewed workaround.
4. Produce a saved execution plan:

   ```powershell
   terraform plan -out=training.tfplan
   terraform show -no-color training.tfplan
   ```

5. Review every create, update and delete with the owner. Check selected subscription, both regions, model versions, capacities, public access, role assignees and any unexpected replacements.
6. Compare the plan with the intended inventory: resource group, VNet, user-assigned identity, role assignments, storage account, Azure OpenAI account/deployments and Search service. Do not expect a Foundry project from the disabled module.
7. Secure the plan file because it can contain sensitive values. Obtain explicit human approval of this exact plan before apply.

A plan that creates zero resources is not automatically correct; it may target the wrong state or existing environment. A nonzero Terraform exit code is a failure requiring investigation. If you intentionally use `-detailed-exitcode`, distinguish `0` (no changes), `2` (changes), and `1` (error).

## 5. Apply only the approved plan and inspect Azure

1. After approval, apply the reviewed file:

   ```powershell
   terraform apply training.tfplan
   ```

2. Treat applying a saved plan as the approval boundary: it does not provide another interactive confirmation. Never add `-auto-approve` to make the exercise unattended.
3. Inspect only the required nonsecret outputs:

   ```powershell
   terraform output -raw resource_group_name
   terraform output -raw ai_search_service_name
   terraform output -raw ai_search_endpoint
   terraform output -raw openai_embedding_deployment_name
   ```

4. In Azure portal, confirm that each expected resource exists in the approved group and region. Confirm deployed model versions and actual capacities.
5. On Search, verify effective network and authentication settings. On Storage/OpenAI, verify which identity actually has each role.
6. Grant the interactive lab user the required data-plane roles through the administrator. Configure a Search service identity separately if using identity-based indexer ingestion.
7. Continue with [Lab 5](lab-05.md) to create data-plane objects and prove ingestion/query behavior.
8. Before [Lab 6](lab-06.md), create or select a supported new Foundry project through an approved process. The commented hub-based module is not a drop-in new-project provisioner.

## Troubleshooting and safe cleanup

| Symptom                                 | Diagnosis and action                                                                        |
| --------------------------------------- | ------------------------------------------------------------------------------------------- |
| Provider or module initialization fails | Confirm the full local module tree, approved registry access and constraints                |
| AuthorizationFailed on role assignment  | Deployment needs role-assignment rights; do not remove roles merely to make apply succeed   |
| Model deployment unavailable            | Recheck model lifecycle, selected OpenAI region, deployment type and quota                  |
| Resource name already exists            | Inspect ownership; choose a new training name rather than importing an unknown resource     |
| Search query returns 403                | Inspect data-plane roles and local/Entra authentication; resource Contributor is not enough |
| `allowed_ips` seems ineffective         | The reviewed child resource ignores the input; an owner-reviewed code change is required    |
| State lock error                        | Confirm the lock owner and active runs; do not force-unlock a live operation                |
| Apply partially fails                   | Preserve state, inspect actual resources, and review a fresh plan before retrying           |

1. Stop agent tests and export only sanitized acceptance evidence.
2. Confirm that the state belongs to this training deployment and contains no shared resources.
3. Prepare and review a destruction plan:

   ```powershell
   terraform plan -destroy -out=cleanup.tfplan
   terraform show -no-color cleanup.tfplan
   ```

4. After the owner's explicit deletion approval, run `terraform apply cleanup.tfplan`. This permanently deletes resources listed in that plan.
5. Verify in Azure that the intended resources are gone. Account for locks, soft-delete retention, and resources created outside Terraform.
6. Do not delete the resource group as a shortcut if it contains resources owned by another exercise. Do not discard state while billable resources remain.
7. Remove local plan files and secrets using your approved retention process; preserve necessary state evidence securely.
